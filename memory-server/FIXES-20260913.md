# memory-server 故障排查与修复记录

日期: 2026-09-13

## 一句话结论

记忆系统的**自动抽取链路此前 100% 失效**（库中 18 条记忆全部是 `source=manual`，
`source=conversation` 为 0 条）。共发现 **5 个串联的 bug**，已全部修复，
并把 54 个历史会话全部补处理完毕（新增 234 条自动记忆）。

## 根因清单（按发现顺序）

### 1. 抽取器 prompt 的 `.format()` KeyError —— 致命，静默

`extractor.py` 中 `EXTRACT_PROMPT` 含 JSON 示例 `{"category": ...}`，
但代码用 `EXTRACT_PROMPT.format(text=text)` 渲染。
Python 会把 `{"category"}` 当作占位符 → 抛 `KeyError: '"category"'`，
而外层是裸 `except Exception: return []`，**异常被完全吞掉**，
表现为"抽取永远返回空数组"，无任何日志。

修复: JSON 示例中的花括号转义为 `{{ }}`；并把静默 except 改为打印日志。

### 2. httpx 走系统代理，本地 127.0.0.1 请求被劫持成 502 —— 致命

`httpx` 默认 `trust_env=True`，本机存在挂载的代理配置，
导致所有 `http://127.0.0.1:1234`（LM Studio）请求返回 502，
而 `curl` 同一地址正常（curl 不走该代理）。

修复: `extractor.py` / `embedder.py` 所有本地请求加 `trust_env=False`。

### 3. 本地模型模板要求必须存在 user 消息 —— 导致 400

部分本地模型（qwythos 等）的 jinja chat 模板强制要求 messages 里有 user 角色。
抽取器原本只发一条 `system`，返回 400：
`No user query found in messages`。

修复: 改为 `system`（放抽取指令+对话）+ `user`（"请按上述规则抽取，只输出 JSON 数组。"）双发。

### 4. 抽取模型 max_tokens 过小 —— reasoning 模型拿不到结论

`config.yaml` 里 `max_tokens: 800`。
当前抽取模型是 reasoning 型，会把思维链写进 `content`，
800 token 用完后 JSON 还没开始输出。

修复: `max_tokens: 3000`；同时加固 `_parse_json`，
从后往前扫描所有 `[...]` 片段取第一个合法数组（兼容思维链+围栏）。

### 5. embedding 模型配置错误 + 维度混存 —— 导致检索 500

`config.yaml` 配的是 `bge-m3`（dim 1024），但**该模型从未安装**。
LM Studio 实际只有 `text-embedding-nomic-embed-text-v1.5`（dim 768）。
于是 `embedder` 一路走 `_fallback_embed` 的 hash 降级向量（无语义，检索等于瞎搜）。
之后手工修了配置，但库中残留 1024 维旧向量，
`np.stack` 因维度不一致抛 `ValueError` → 检索接口 500。

修复:
- 配置改为 `text-embedding-nomic-embed-text-v1.5` / `dim: 768`
- 新增 `reembed.py`：把库里维度不符的向量重嵌入
- `store.load_embeddings()` 加固：按主流维度过滤脏数据，不再 500

### 6. 抽取模型触发 LM Studio 内存护栏

`gemma-4-26b-a4b-it-mlx`（15.6G）在 32G 机器上会被 LM Studio 加载护栏拦下
（`insufficient system resources`），且启动时不预加载会导致超时。

修复: 抽取模型换为 `qwythos-9b-claude-mythos-5-1m-optiq-5bpw-mlx`（6.9G，稳定）。

## 二次优化: 记忆质量

首轮补处理出了 436 条，但大量是碎片
（"增加评测场景"、"用户名为 gavin"、"看着还行"），
缺乏上下文、无法跨会话复用。

重写 `EXTRACT_PROMPT`，加入"长期价值把关"：
明确列出**不该抽**的类别（单次任务临时诉求、寒暄确认、
一次性报错/文件名/命令、脱离上下文无法理解的碎片、助手自己的言行），
并要求 content 自包含。

重跑后 **226 条**（v1 436 条 → v2 226 条），信噪比接近翻倍。

# 第二次巡检与加固（2026-09-27）

## 巡检结论

服务本身健康（端点全 200、366 条向量维度统一、检索链路通畅），
但发现 **2 个新缺陷**，均已修复。

## 新发现的问题

### 7. 抽取模型不会自动加载 —— 空闲卸载后抽取全挂

**现象**: 日志刷满 `400 Bad Request`（累计 30 次）。
LM Studio 会在 TTL 到期后空闲卸载模型，此时 chat 接口返回
`{"error":"Model is unloaded."}`（HTTP 400），
而 `extractor` 没有像 `embedder` 那样的加载逻辑，
于是**只要模型被卸载，所有自动抽取静默失败**。

**修复**: 给 `Extractor` 加 `ensure_loaded()`（复用 `lms` CLI 逻辑）：
- 调用前先查 `lms ps`，未加载则 `lms load <model> -y --ttl 1800`
- 命中 400 + "unloaded" 时，立刻重载并重试一次（覆盖竞态）
- 加载失败后 60s 内不重试，避免每条消息都阻塞在加载上

新增配置项: `extract.auto_load: true` / `extract.ttl_seconds: 1800`

**验证**: 在 LM Studio 无任何 LLM 加载的状态下调用 `/api/extract`，
日志显示 `[extractor] 已自动加载 ... (ttl=1800s)`，抽取成功，耗时 27s。

### 8. 去重仅靠精确匹配 —— 同义改写会重复入库

**现象**: 同一事实两次抽取（措辞略不同，如"不要问我是否确认"
vs "别来问我是否确认"）会被当成两条独立记忆重复入库。

**修复**: `/api/extract` 改为**双重去重**:
1. 精确匹配（content 全等）
2. **语义去重**: 向量 cosine ≥ `DEDUP_SIM` 视为同一条
   - 批量内也会互相比对，避免同批次自重复

**阈值标定** (`DEDUP_SIM = 0.88`)，实测:

| 类型 | 相似度 | 判定 |
|---|---|---|
| 同义句（应去重） | 0.895 | 去重 ✓ |
| 近义偏好（应去重） | 0.995 | 去重 ✓ |
| 相关但不同（应保留） | 0.712 | 保留 ✓ |
| 同主题不同事实（应保留） | 0.648 | 保留 ✓ |

注意: nomic 对中文区分度偏弱（近义句只有 ~0.89，留余量不大），
若之后换 embedding 模型需重新标定该阈值。

## 附带清理

- 删除误抽的垃圾记忆（任务性数据/工具输出回显/无上下文碎片），
  如 `app.log contains 624 WARN lines`、`任务9出现频率最高`、
  `使用 read 工具读取文件` 等
- 清理后再无长度 < 12 字符的无上下文碎片

# 第三次升级：中文 embedding + LM Studio 稳定性加固（2026-09-28）

## 需求

1. 把 embedding 换成中文擅长的
2. LM Studio 不稳定 → 增加稳定性能力

## 一、embedding 换成 bge-m3

### 为什么换

原用 `text-embedding-nomic-embed-text-v1.5` 是英文向模型，中文区分度明显不足。

**中文梯度区分度实测对比**（越能拉开差距 = 越会区分）：

| 用例 | bge-m3 | nomic | 谁更好 |
|---|---|---|---|
| 同义句（应高） | **0.986** | 0.911 | bge |
| 近义偏好（应高） | 0.914 | 0.995 | 都高 |
| 中文语义（应高） | 0.907 | 0.994 | 都高 |
| 相关但不同（应中低） | **0.653** | 0.712 | bge 分得更开 |
| 无关（应低） | **0.476** | 0.527 | bge 更干净 |

关键差异：nomic 把大量中文都压进 0.99 高相似区（区分度差，去重阈值余量极小）；
**bge-m3 能拉开 0.476~0.986 的梯度**，检索和去重都更准。

### 安装过程（踩坑记录）

LM Studio 的 staff picks 库里**搜不到** bge-m3（`lms get bge-m3` 全部报
"No staff picks found"），HuggingFace 直连也不通（`huggingface.co` 返回 000）。

最终发现 `~/.lmstudio/models/gpustack/bge-m3-GGUF/` 下已有一个**未完成的下载**
（`.part` 文件）。让它继续下载完成后，lms 自动识别为 `text-embedding-bge-m3`
（567M, BERT, Q8_0, 634MB）。

结论：LM Studio 上装中文 embedding 走 `gpustack/bge-m3-GGUF` 这条路可行，
但需要耐心等下载（约 635MB，实测下载速度约 5-6 MB/分钟）。

### 变更

- `config.yaml`: model → `text-embedding-bge-m3`，dim 768 → **1024**
- `reembed.py` 全量重建索引：373 条记忆 768 → 1024 维
- 去重阈值随之重标定：**0.88 → 0.95**
  （bge-m3 下同义句 0.986、相关但不同 0.653，取 0.95 余量充足；
   对比 nomic 时代 0.88 的余量极小，稳健性大幅提升）
- 去重阈值改为配置项 `dedup.sim_threshold`，换模型时无需改代码

## 二、LM Studio 稳定性加固

### 新增 stability.py —— 自愈守护模块

统一管理模型生命周期，解决 5 类不稳定问题：

| 问题 | 解法 |
|---|---|
| 空闲 TTL 到期自动卸载 | 守护线程定期巡检 + 保活 |
| 大模型触发内存护栏加载失败 | 识别 `insufficient system resources` 并给出提示 |
| 加载异步，load 完立刻请求会打到 unloaded | 冒烟测试确认接口真可用后才返回 |
| 服务重启后模型不回来 | 启动即巡检并拉起 |
| HF 直连不通 | 走 LM Studio Hub / 本地已装模型 |

提供的核心能力：

- **`ensure(model)`**: 幂等加载，带 3 次重试 + 指数退避（5s/10s/15s）；
  失败后 60s 内不再重试，避免每条消息都阻塞在加载上
- **`HealthDaemon`**: 后台守护线程，默认每 60s 巡检，掉线自动拉起
- **`is_unloaded_error(e)`**: 精准识别"模型未加载"类错误（含多种 LM Studio 文案）
- **`_smoke_test()`**: 加载后真实打一次接口，避免"ps 显示已加载但接口不可用"
- **`_norm_id()`**: 归一化 `bge-m3:2` 这类实例后缀，避免误判为未加载

### 改造点

- `embedder.py`: 删除自带的 lms 逻辑，委托 stability；
  **模型未加载时自动重载重试**，不再直接降级到无语义 hash 向量
  （历史 bug：bge-m3 从未安装，全程静默走 hash 降级导致检索等于瞎搜）
- `extractor.py`: 同样委托 stability
- `app.py`: 启动时 `stability.start_daemon()`，并新增 **`/api/health`** 端点
- `config.yaml`: 新增 `embedding.auto_load` / `stability` 段
  （healthcheck_interval / auto_load_retry / retry_backoff / keepalive_ttl）
- **新增 `run.sh`**: 进程级守护启动器，崩溃自动重启

### 自愈验证（两个场景，均通过）

**场景 1: 运行中手动卸载** → 下次请求触发自动重载，检索正常返回。

**场景 2: 全部卸载 + 重启服务（最严苛）**
```

[stability] 巡检发现 text-embedding-bge-m3 不在线, 尝试拉起
[stability] 加载 text-embedding-bge-m3 (第 1/3 次, ttl=3600s)
[stability] ✓ text-embedding-bge-m3 已就绪
[stability] 巡检发现 qwythos-9b-claude-mythos-5-1m-optiq-5bpw-mlx 不在线, 尝试拉起
[stability] ✓ qwythos-9b-claude-mythos-5-1m-optiq-5bpw-mlx 已就绪

# 第四次修正：消除模型反复卸载/重载（2026-09-28）

## 现象

巡检 `/api/health` 发现异常指标：**守护线程巡检 2797 次、revive 94 次**。
即服务运行约 2 天里，模型被反复卸载又拉起 94 次。

## 排查

日志显示两个模型**成对交替掉线**：

```
[stability] 巡检发现 text-embedding-bge-m3 不在线, 尝试拉起
[stability] ✓ text-embedding-bge-m3 已就绪
[stability] 巡检发现 qwythos-9b-... 不在线, 尝试拉起
[stability] ✓ qwythos-9b-... 已就绪
（如此循环）
```

**逐一验证假说**：

| 假说 | 验证结果 |
|---|---|
| `lms load` 会踢掉已有模型？ | ✗ 实测不会（会创建 `:2` 新实例，旧模型保留） |
| 两个模型无法共存？ | ✗ 实测可同时 loaded |
| **TTL 到期卸载？** | ✓ **确认** |

根因是 **TTL**：`config.yaml` 里设 `ttl_seconds: 3600`，
而 LM Studio 全局 `developer.jitModelTTL` 也是 `3600000`（1 小时）。
两者同时到期 → **每小时两个模型一起被卸载，又一起被守护线程拉起**。
94 次 revive ≈ 47 小时 ≈ 2 天，完全吻合。

## 修复

### 1. 改为常驻模式（根治）

`lms load` 的 `--ttl` 参数**不传时模型常驻**（`lms ps` 显示 `TTL: Local`）。
bge-m3 仅 635MB、qwythos-9b 6.94GB，合计 7.6GB / 32GB 内存，完全放得下。

- `stability.ensure()` 支持 `ttl <= 0` 时不传 `--ttl`（常驻加载）
- `config.yaml`: `embedding.ttl_seconds` 3600 → **0**；
  `extract.ttl_seconds` 1800 → **0**；`stability.keepalive_ttl` 3600 → **0**

### 2. 守护线程改为逐个拉起（防互踢）

原先一轮巡检会依次拉起所有掉线模型。虽然实测 `lms load` 不踢模型，
但为了稳健（不同 LM Studio 版本行为可能不同，且全局
`unloadPreviousJITModelOnLoad = true` 确实存在），改为
**一轮最多拉起一个，剩余等下轮**，避免任何潜在的互相挤掉。

## 验证

```
起始 revives = 2
第 1 分钟: revives/checks = 2 / 4
第 2 分钟: revives/checks = 2 / 5
第 3 分钟: revives/checks = 2 / 6
```

**checks 递增但 revives 恒定在 2** —— 模型稳定常驻，不再反复加载。
`lms ps` 两个模型均显示 `TTL: Local`。

## 结论

至此记忆系统全部已知问题清零：
- 抽取/检索/去重三条链路端到端验证通过
- embedding 换为中文更强的 bge-m3
- 自愈守护可用（零模型状态下 10 秒自动恢复）
- 模型常驻，无周期性抖动
